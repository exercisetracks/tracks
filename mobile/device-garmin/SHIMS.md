# The boundary between vendored Gadgetbridge code and Tracks

**Status: both sides of the boundary exist and the APK links them.** 205
vendored Java/Kotlin files, 194 generated FIT message classes, ~40 shims in
`src/compat/java`, and `com.tracks.device.garmin` on top.

This is the map of what we took, what we replaced, and why — kept because the
"why" is the part that a future refresh needs and a diff cannot show.

## How the pieces fit

```
src/main/java/nodomain/…    vendored, never edited (except the recorded patches)
src/compat/java/nodomain/…  our replacements, same package names
src/main/res/values/…       generated from upstream's strings.xml
build/generated/fit/…       generated by :fit-codegen from Garmin's profile JSON
src/main/java/com/tracks/…  Tracks' side of the boundary
```

The one rule that keeps this honest: **nothing under `nodomain` may import from
`com.tracks`**, with a single documented exception (`CalendarManager`, below).
The reverse is free — `com.tracks.device.garmin` exists precisely to know both
worlds.

Shims live in `src/compat`, **not** under `src/main/java`, because
`pull-gadgetbridge.sh` deletes the vendored package tree wholesale before each
refresh — anything of ours in there would vanish with it.

The module's Gradle `namespace` is `nodomain.freeyourgadget.gadgetbridge`. That
is deliberate: the namespace is what AGP names the generated `R` class after, and
the vendored code imports `nodomain.freeyourgadget.gadgetbridge.R` some 600
times. Setting it here means those resolve against a real generated `R`, with no
hand-written forwarding class to maintain.

## The four shims that carry the weight

| Shim | Replaces | Why not vendor it |
|---|---|---|
| `GarminSupport` | the orchestrator | Upstream's reaches into the application singleton, greenDAO, preference screens and the activity UI — in Gadgetbridge it *is* the app's view of the watch. Ours owns the connection and the handlers and hands everything outward as an event. |
| `AbstractDeviceSupport` | 654 lines | Almost all of it turns a device event into a broadcast, a database write, or a notification. Tracks answers all three differently. Ours is a listener fan-out. |
| `GBDevice` | device model | State holder. Upstream's broadcast becomes a listener callback: Tracks reports connection state as a Flow, and a system broadcast would leak device addresses to any app listening. |
| `util.GB` | 707 lines | Toasts and notification channels wearing a utility class's name. Logging kept, UI no-op'd. |

## Decisions worth remembering

**Phone GPS is never read.** `GBLocationService` is inert by design. Continuous
GPS is the most expensive thing an Android app can do short of keeping the screen
lit, and an expedition tool that flattens the phone to duplicate a sensor the
watch already has is worse than useless — the phone is also the map.

**The HTTP proxy refuses everything.** The watch can ask the phone to fetch
arbitrary URLs. Honouring that would make Tracks an open proxy reaching Garmin's
servers from the user's phone, which contradicts the whole premise of a
self-hosted app. Weather arrives over GFDI from Breezy Weather instead.

**Sleep as Android is not integrated.** `getSleepAsAndroidSender()` returns null,
which is upstream's own "not configured" signal, so every call site skips. The
methods on the shim throw rather than silently no-op: they are unreachable while
the getter returns null, and if that changes, an exception naming the class beats
sleep data being quietly dropped.

**Calendar sync is real.** `CalendarManager` bridges to Tracks'
`com.tracks.device.feeds.CalendarReader`, which queries `CalendarContract.Instances`
rather than `Events` — the difference matters, because a recurring event is one
row in Events and one row per occurrence in Instances, and a watch wants
occurrences. This is one of the few places the `nodomain` namespace deliberately
reaches into `com.tracks`; the alternative is a second calendar query with its
own idea of recurrence.

## What was measured and dropped

Two files were vendored first and removed after measuring what actually reached
them. Both are recorded in the manifest:

- **`AndroidUtils`** — exactly 1 of 13 public methods is reachable. The rest is
  theming and file sharing, and it was the largest source of resource references
  outside `ActivityKind`, pulling in Material3 and androidx.cardview.
- **`DateTimeUtils`** — 5 methods reachable, none of them the two needing
  `com.github.pfichtner:durationformatter`, which resolves through JitPack.
  JitPack builds are not reproducible, which matters because F-Droid is the
  eventual target.

Also dropped: every concrete `service/btle/profiles/` implementation (PineTime
filesystem, blood pressure, weight scale, thermometer, heart rate). Nothing
outside that package references any of them, and together they dragged in
kotlin-parcelize, zip/URI helpers and PineTime constants.

## The patches

Editing a vendored file is a standing cost, so there are only a few, all in
`vendor/patches/` and all re-applied by the pull script — which **fails loudly**
if one stops applying, rather than silently shipping an unpatched refresh.

1. **`CommunicatorV2`** — strips Gadgetbridge's realtime activity-sample store.
   Samples reach the Tracks server inside the FIT files we upload; a second store
   would need reconciling, and there is no UI listening for the broadcast.
2. **`GBTarFile`** — `java.util.Arrays` instead of a *shaded* Bouncy Castle copy,
   for one `copyOfRange`. Dropping a crypto library from the APK for an array
   copy is worth a one-line patch.
3. **`MlrCommunicator`** — one `private record` becomes a plain final class.
   This one is not a design choice, it is a toolchain wall: desugaring a record
   for minSdk 26 makes D8 emit a *global synthetic*, and AGP dexes library
   modules through an artifact transform that has nowhere to put one. The build
   fails outright with "Attempt to create a global synthetic for 'Record
   desugaring' without a global-synthetics consumer". Every use of the type is
   direct field access inside the enclosing class, so the rewrite is
   behaviourally identical.
4. **`FileSyncServiceHandler`** — one `else` branch calling
   `deviceSupport.onFileListComplete()`. The newer protobuf sync asks the watch
   for a file list and gets the answer back asynchronously; nothing on the wire
   marks the end of that exchange. Upstream never needs to know, because it only
   ends a sync run once a file has actually transferred. Tracks ends a run when
   the queue drains — which is what makes "the watch had nothing new" terminate
   instead of hanging — so it has to be able to tell "the queue is empty" from
   "the queue is empty *so far*".

   This is the one patch that is a real fork of behaviour rather than a
   toolchain workaround, so it is the one most likely to conflict on a refresh.
   If it does: the hook belongs wherever `handleFileListResponse` decides there
   are no further pages.
5. **`ProtocolBufferHandler`** — two preference reads become
   `deviceSupport.newSyncProtocol()`. Upstream treats the protocol as a setting
   and reads the key wherever it needs the answer; Tracks decides it once per
   connection from what the watch can actually do, so a raw read here answers a
   different question. It got this wrong in the loudest possible way on the
   first watch that had no preference set: the app requested a file list over
   the newer protocol and this half logged "Ignoring file sync service — new
   sync protocol is disabled" for every reply the watch sent back.

   If it conflicts on a refresh, the rule is the accessor, not the key: any
   vendored code asking whether this connection speaks the newer protocol must
   ask `GarminSupport`.

6. **`FileSyncServiceHandler`, again** — Tracks' own sync behaviour in the
   listing handler, which had been edited in place and was recorded only on
   2026-09-30 (a refresh would have dropped it silently): a per-page tally on
   logcat, type names resolved through `GarminSupport`'s persisted map, the
   upload-response listener, and the recovery listing — an unfiltered listing
   after the normal one, from the page id the last one ended on, that takes
   any activity Tracks has never downloaded. That last part is what brings in
   activities a watch's own Wi-Fi Auto Upload has already flagged synced
   (docs/garmin-ble-protocol.md). If it conflicts on a refresh, the recovery
   listing belongs wherever `handleFileListResponse` decides there are no
   further pages, before `onFileListComplete`.

   Regenerated by rebuilding upstream 0.93.0 plus patches 0001–0005 in a
   scratch tree and diffing the current file against it; upstream plus all
   six patches reproduces the file byte for byte.

7. **The music-server proxy** (`http/GarminHttpRequest`, `GarminHttpResponse`,
   `GarminJson`, `GarminJsonException`) — the watch's HTTP requests are
   declined except to the one music server the user configured, whose
   requests Tracks forwards; the request body is decoded before it is passed
   on. Everything else the watch asks for over the phone (Garmin's own
   services) is still refused. See `WatchHttpProxy`.
8. **Transfers: what the watch said, and getting it there faster**
   (`FileTransferHandler`, the create-file / upload-request / transfer-data /
   set-file-flags status messages, `CommunicatorV2`, `MlrCommunicator`,
   `CompressionUtils`) — the watch's own reason for refusing an upload is
   kept and exposed instead of logged and dropped, as is its answer to a
   set-file-flags request; transfer handles can be closed when an upload
   drains rather than after a 30 s timeout; the MLR layer reports when its
   queue drains and fills its send window, with upload chunks sized to the
   negotiated MTU (a 140 KB watch app went from ~9 minutes to ~50 s);
   `CompressionUtils` gains `deflate`, the upload half of the zlib format
   the transfer channel uses.
9. **`FileType`'s pull rules** — which types an ordinary sync fetches, the
   user-triggered widening for courses and places, and the training calendar
   read back on every sync (see the comments on `alsoPull`).
10. **`ProtocolBufferHandler`** — a watch-app delete reports its result to
    `GarminSupport` (which the "remove watch app" screen waits on) instead of
    re-requesting the app list, and the watch's calendar request is logged
    with its window and limits, since those decide how much agenda appears.
11. **Robustness** (`TransactionBuilder`, `MusicControlCapabilitiesMessage`)
    — a BLE action queued just after the device support was disposed is
    dropped with a log line instead of crashing on a null queue, and a
    music-capabilities request with an empty payload is read as "none"
    instead of throwing.
12. **Proto definitions** (`gdi_explore_sync`, `gdi_file_sync_service`,
    `gdi_smart_proto`) — fields Gadgetbridge stubs or leaves out that Tracks
    reads and writes: Explore sync's start-sync details and collection
    messages, file-sync upload and transfer-complete fields, the services
    the calendar push needed.

13. **`FitDefinitionStatusMessage`** — a watch's answer to a FIT definition
    that carries only a status and no definition status code is read as "not
    applied" instead of throwing. A fenix 6X sends one now and then: 9 bytes,
    `090088139313054085` — RESPONSE to FIT_DEFINITION, status 5
    (LENGTH_ERROR), CRC. Upstream reads the code byte unconditionally, ran off
    the end of the payload, and the message was dropped as unparseable; once
    that coincided with a sync stalling (now covered by the file-list
    watchdog in `GarminSupport`). Parsed, it reaches `FitLocalMessageHandler`,
    which treats anything but APPLIED as upstream does: it logs and sends the
    data anyway, and unregisters on the data's status. The same patch makes
    `generateOutgoing` return before writing when the message is one the
    watch sent, since `GarminSupport` asks every parsed message for its reply
    and this one has no code to write. Upstream master has no fix of its own:
    checked at `0d2cd20c0` (2026-09-30), the file and its dispatcher in
    `GFDIStatusMessage` are unchanged since 0.93.0 and still read the code
    byte unconditionally. On a refresh, drop this patch if upstream reads
    the code only when present. Verified by `FitDefinitionStatusMessageTest`,
    not yet on a watch.

Patches 7–12 record edits that were made in place between August and
September 2026 and found on 2026-09-30; until then a refresh would have
reverted every one of them silently.

## Keeping it that way

`vendor/gadgetbridge.lock` holds the sha256 of every vendored file (Java,
Kotlin and proto) as upstream plus these patches produce it.
`VendoredLockTest` checks the tree against it on every unit-test run, offline,
so an edit to a vendored file that is not recorded as a patch fails the build
the day it is made. `pull-gadgetbridge.sh` runs `check-vendored.py
--verify-lock` before it overwrites anything, and refreshes the lock after.

To change a vendored file: edit it; rebuild the baseline and write the patch
(`check-vendored.py <checkout>` reports what differs); add a paragraph here;
then `check-vendored.py <checkout> --write-lock`. The checkout must be at the
release in `VENDORED.md`.

## Generated, not checked in

**FIT message classes.** Upstream checks in four and generates the rest at build
time. Even those four are halves — `FitRecord extends AbstractFitRecord`, and the
parent is generated. `:fit-codegen` is a plain JVM module so neither the
generator nor its 300 KB profile JSON reaches the APK.

**Android resources.** `vendor/generate-gb-resources.py` scans the vendored tree
for `R.string`/`R.drawable` references and emits them: strings copied from
upstream, drawables aliased to one placeholder of our own, since Gadgetbridge's
artwork is under a separate licence we do not vendor.

That script fails the build rather than substituting a plausible-looking label
when a string cannot be found. This is not paranoia — most of those names are
display text where a wrong guess is cosmetic, but some are protocol constants
(`pref_media_play_value` = `"PLAY"`) that get compared against stored preferences
and sent to the watch. A derived label there breaks silently. It caught exactly
that during the first run: eleven of them live in `values.xml` as
`<item type="string">`, not in `strings.xml`.

## Tracks' side: `com.tracks.device.garmin`

Four files, and the split between them is the point.

| File | Job |
|---|---|
| `GarminIntegration` | Implements `DeviceIntegration`. The only class that sees both worlds. |
| `GarminWeatherEncoder` | Tracks' `WeatherReport` → FIT local messages. |
| `GarminNotifications` | Tracks' `DeviceNotification` → `NotificationSpec`. |
| `GarminFileTypes` | Which Garmin file type a server-supplied file is. |

**The pull contract changed shape.** `DeviceIntegration` originally had
`listFiles()` and `pullFile()`, which is how a filesystem behaves and is not how
any of these watches behave. Garmin's protocol has no addressable read: you ask
the watch to sync, it streams a directory, and files arrive one at a time as the
transfer state machine works through them — landing on disk as a side effect
rather than being returned. So the contract is now `pullAll()` plus a
`pulledFiles` flow, which is also the shape Coros will need.

**Nothing is archived on the watch until Tracks says so.** Gadgetbridge archives
a file as soon as it transfers. `GarminIntegration` waits for `confirmPulled`,
which the sync layer calls once the bytes are durably held elsewhere. Until then
the watch holds the only copy that survives losing the phone — on an expedition
that distinction is the whole ballgame, and flash on a modern watch is not
scarce enough to trade it for.

**Pushes are typed from the file, not the folder.** The server describes a
pushable file by the folder a *cable* sync would write it to, and
`GARMIN/NewFiles` carries workouts, schedules and race plans indiscriminately.
BLE has no folders — `CreateFileMessage` addresses a numeric type — so
`GarminFileTypes` reads the FIT `file_id` message, which is authoritative, and
falls back to the folder only when parsing fails.

**Upload outcomes come back through `GB.updateInstallNotification`.** That is
the only place the vendored upload state machine reports anything, and success
and failure are identical except for the notification text. The `GB` shim
classifies them against the same string resources the caller used, so the Tracks
side gets a typed outcome instead of doing string comparison. An unclassifiable
outcome counts as failure, because a push reported as delivered stops the server
offering the file — and the workout then silently never reaches the watch.

## Where a file goes after it leaves here

Both directions now reach the server, and they use different credentials on
purpose:

```
watch → GarminIntegration.pulledFiles → WatchManager.uploadPulled
      → WatchUploader (seal with the user's public key)
      → POST /sync/ingest          [agent token, no vault, no session]
      → confirmPulled → archive on watch + delete the phone's copy

server → GET /device-sync/upload-list [JWT, needs a session]
       → GarminIntegration.pushFile → watch
       → POST /device-sync/mark-uploaded
```

The pull side deliberately needs neither a session nor an open vault — it seals
with a public key and the server queues a blob it cannot read until the user
next logs in. That is what makes an upload work three weeks into a trip. The
push side does need a session, which is the right way round: a planned workout
that fails to arrive is a nuisance, an activity that fails to upload is lost.

Both sides mark *after* the other end confirms, never before. On the push side
that ordering matters more than it looks: the server stops offering a file it
believes was delivered, so marking optimistically means a workout that silently
never arrives and never retries.

## What is next

1. **Validate against real hardware.** The transport is written; none of it has
   met this watch. This is the step that actually decides whether any of it is
   right.
2. **Background sync.** Today it is a button. Doing it while the phone is in a
   pocket needs WorkManager plus a `connectedDevice` foreground service, because
   Android will not let a long BLE transfer run otherwise.
3. **AGPS.** Ephemeris arrives over the HTTP path Tracks refuses to proxy.
   Serving *only* a server-supplied file from local storage would close the gap
   without reopening a proxy to Garmin. `capabilities.assistedGps` says `false`
   until then.

```bash
cd mobile

    device-garmin/src/main/java \
  | sed 's/^import nodomain.freeyourgadget.gadgetbridge.//' | sort | uniq -c | sort -rn
```
